- [ ] **(Phase 5/6, UI) Wire `CombinationInfo` export to a download button.** The two
      _export-only_ serializers already exist in `io.ts` (`combinationInfoToJson`,
      `combinationInfoToCsv`); what remains is the browser plumbing. Decided UX: no separate
      export params — the property picker drives `getCombinations`, that result _is_ the
      rendered table, and the download button serialises **whatever `CombinationInfo` is
      currently shown**. `CombinationInfo` is never re-imported: to reload data a user
      re-uploads `CharacterInfoShort[]` (CSV/JSON) and we recompute. JSON export keeps the
      full nested wrapper (incl. each entry's `characters[]`); CSV export is the flat table
      view — columns `[label, ...selected properties, count, characters]`. `label` leads as
      the row's stable composite key (redundant with the property columns by design — easy
      to delete a column, hard to recompute a key); `characters` is the `", "`-joined
      character names (full objects live only in JSON). Reserved column names: `label`,
      `count`, `characters`. Same name-squashing the table display will likely need.

- [ ] **(Phase 5, UI) Handle the profession/armor correlation.** Armor is _derived_ from profession, so selecting both and filling produces 27 rows of which 18 are structurally impossible (`Guardian-Light` can never exist). Correct per spec - filling is the user's choice - but the property picker should discourage it: grey out `armor` once `profession` is selected (or vice versa), or at least keep that pairing out of the defaults. Every other property pair is independent; these two are the only correlated ones.

- [ ] **(Phase 4, UI) Validate the API-key input in the form.** Disable submit on an
      empty/whitespace-only key so the client-side guard is never the user's first
      feedback. The guard lives in `Gw2ApiClient`'s private `request()` (not the
      constructor) deliberately: an empty key is not something _we_ detect - the API
      returns `401 {"text": "Invalid access token"}` for it, which maps to the same
      `kind: "invalid-key"` - so the guard only saves a doomed round trip and must not
      reshape the public contract. Keeping it at the request site also gives one error
      channel for the whole "your key doesn't work" family (empty, malformed, revoked,
      expired, wrong scope), only the first of which is knowable without the network;
      avoids a throw during render once the client is built in a `useMemo`; and leaves
      key-less endpoints (e.g. `/v2/build`) constructible. Keep the check dumb
      (`.trim() !== ""`) - never validate the _shape_ of a key, since a well-formed key
      can still be revoked, so shape checks are UX only and belong in the form.

- **2026-08-31 - Phase 2 (unit 2b): MSW mocking & the test layer.** Built `src/lib/gw2/api.test.ts` (13 tests; 127 green). **MSW** (Mock Service Worker) mocks the GW2 API at the fetch layer: a shared `src/test/setup.ts` holds `setupServer()` (no default handlers - tests register their own via `server.use`) plus the three lifecycle hooks (`listen`/`resetHandlers`/`close`), wired through `setupFiles`; `onUnhandledRequest: "error"` fails any un-mocked request; env stays `node` (no jsdom - `setupServer` intercepts Node's native fetch). **`Omit<T, K>`** models the wire-vs-domain split: the mock body omits derived `armor` (`Omit<CharacterInfoShort, "armor">` - still type-checks every other field), and `expected` spreads it back plus a **literal** armor (hardcoded, not recomputed via `armorForProfession` - don't recompute the expectation with the code under test). **Asserting a thrown custom error - two idioms**: try/catch + `expect.unreachable` + `if (!(err instanceof Gw2ApiError)) throw err` (the guard both narrows - `catch` is `unknown` under strict - and re-throws on the no-throw path, so the test can't pass vacuously; the only form that asserts type identity) vs the terser `rejects.toMatchObject({ kind })`. **`malformed` from three code paths** tested separately (`.json()` rejects; not-an-array; per-element validation). **Validation order matters**: the bad element must be otherwise-complete to _reach_ the field you mean to break, and asserting the wrapped **`cause`** proves _which_ thing failed. **Gotcha**: vitest asymmetric matchers (`expect.objectContaining`/`stringContaining`) are typed `any` -> trip `no-unsafe-assignment` (lint, not `tsc`) -> use a concrete literal, which `toMatchObject` partial-matches anyway. **The CORS guard** is the one test MSW can't replace (it doesn't enforce CORS): capture the outgoing `Request`, assert no `authorization` header + `access_token`/`v` in the query; narrow the capture with `if (!captured) throw` (not `!`, which `no-non-null-assertion` forbids). **Empirically confirmed**: Node rejects `AbortSignal.timeout()` with a `DOMException` named `"TimeoutError"` (tested via `delay("infinite")` + small `timeoutMs`). See [lesson 06](./.lessons/06-phase2-api-layer.md).
- **2026-07-28 - Phase 2 (unit 2a): the `fetch` client, CORS & closing the `any` holes.** Built `src/lib/gw2/api.ts` - `Gw2ApiClient` + `Gw2ApiError`. **Headline finding**: the browser **can't send `Authorization: Bearer`** - it makes the cross-origin GET a _preflighted_ request, and the GW2 backend 404s the OPTIONS probe with no CORS headers, so the real request never leaves; the key + schema go in the **query string** (`?access_token=`, `v=`), which keeps it a _simple_ request. **`fetch` is not `requests`**: it doesn't reject on 4xx/5xx (check `response.ok` yourself - the missing `raise_for_status`); it rejects only on transport failure (a deliberately vague `TypeError`); `.json()` is itself async and can reject (own try/catch); there's no `timeout:` option -> `AbortSignal.timeout(ms)`. **Error design**: `extends Error` + a `kind` discriminant the UI switches on + `{ cause }` to wrap without swallowing. **Key-leak fix**: a `URL` stringifies to its full href (query string included), so derive a safe `origin + pathname` _before_ the key enters `searchParams`, and never touch `url` after. **Closed the `any` holes globally**: `src/unknown-globals.d.ts` re-declares `JSON.parse`, `Body.json()`, and `Array.isArray` to yield `unknown` via interface merging (no lib patching). **The lesson that outranks the rest**: typecheck + lint were both clean while three blocking bugs remained - the toolchain proves code _well-typed_, never _correct_. See [lesson 06](./.lessons/06-phase2-api-layer.md).
- **2026-07-25 - Phase 1: CSV / JSON IO (closes the pure-logic layer).** Built `src/lib/gw2/io.ts` + tests (114 green). **Design before code**: the round-trippable form is the raw `CharacterInfoShort[]` (JSON _and_ CSV), never the `CombinationInfo` wrapper - the wrapper is derived and reproducible, so we persist the source and recompute; `CombinationInfo` export is one-way (JSON = full nested wrapper, CSV = the flat table). **Pure vs DOM split**: everything is string ↔ domain (`*ToJson`/`*FromJson`, `*ToCsv`/`*FromCsv`); the File API (picker, Blob download) is a thin Phase-6 wrapper over these, so the whole layer is unit-testable now. **Every read path re-validates through `parseCharacterShort`** - types are erased, a parsed string is untrusted. **`JSON.parse` is a hole**: it's typed `any` (not `unknown`), silently re-opening everything the validator closed - annotate the result `: unknown` immediately to re-close it (and `Array.isArray` on `unknown` narrows to `any[]`, so cast to `unknown[]` before the loop). **CSV has no types**: every cell is a **string**, so `level`/`age` need explicit coercion before the validator - and JS number coercion is a minefield: `Number("")` is **0** (not NaN), `Number("abc")` is **NaN** whose `typeof` is `"number"` (so it'd pass a `typeof` check!), and `Number("Infinity")`/`"1e999"` are **Infinity** - guard with `Number.isFinite`, **not** `!isNaN`. **PapaParse** (widely-used browser CSV lib; `import * as Papa` - no default export) does the RFC-4180 quoting so we don't hand-roll it; `header: true` gives rows keyed by column **name**, which makes extra columns and any column **order** free to tolerate (index by name, not position) and drops extras via the validator's fresh-object rebuild; `transform: (v) => v.trim()` deliberately tolerates the near-universal "space-after-comma" hand-authored CSV (a spec deviation justified because our domain has no meaningful surrounding whitespace). **`CombinationInfo` CSV** flattens to `[label, ...properties, count, characters]`: `label` leads as a stable composite key (redundant with property columns by design - deleting a column is easy, recomputing a key isn't); dynamic columns built from `info.properties`; `characters` squashed to `", "`-joined names (Papa quotes that comma-containing cell automatically). **Testing lessons reinforced**: never recompute the expectation with the implementation's own logic (assert the observable 2-space indent, not `JSON.stringify(...)` again); construct a function's test input **independently of its inverse** (hardcode the JSON/CSV string), except in the round-trip test where composing both _is_ the point; `toStrictEqual` > `toEqual` (catches `undefined`-vs-absent fields); assert the throw **message**, not bare `toThrow()`, so a test proves it failed for the _right_ reason; **you can't parse CSV with `.split(",")`** - a quoted field's internal comma breaks it (the exact hazard quoting exists to solve); `Papa.unparse` emits **CRLF** per spec, so split fixtures on `/\r?\n/`; template literals keep _all_ indentation (no auto-dedent), so build multi-line CSV fixtures as an array of lines `.join("\n")`. Extracted a shared `character()` factory to `testutils.ts` (test-data-builder pattern), and promoted `assert` to its own `asserts.ts` leaf module (generic utility, not validation surface). See [lesson 05](./.lessons/05-phase1-csv-json-io.md).
- **2026-07-20 - Phase 1: combinations, immutability & the cartesian product.** Built `src/lib/gw2/combinations.ts` + tests (85 green). **Design before code**: a "combination" is a group-by of present data, with `fillBlanks` optionally completing the grid; empty `properties` means "don't subdivide", not "info missing"; the row `label` is a stable **id / export handle**, not the table's display source. **Choosing the type deleted runtime code** - typing `properties` as a fixed categorical union instead of `list[str]` turned three of Python's four `ValueError` guards into compile errors or impossibilities. **`keyof typeof`**: the object analog of lesson 02's `(typeof ARR)[number]` - one `as const` registry is the single source of truth for both the property union and the fill step's value lists; plus the `Record`/`Partial` utility types. **The widening trick returns**: indexing a registry with a union key yields a _union of `as const` tuples_, and `.map`/`.indexOf` on it is "not callable" - annotate `readonly string[]`, exactly as lesson 03 did for `.includes`. **`for...of` vs `for...in`**: Python's `in` is JS's `of`; `for...in` yields **string keys** ("0", "1"), and TS types it `string` (never `keyof T`) for soundness - a typo here was caught by the type system, not a test. **Grouping idioms**: `Map` over `{}` (no prototype-key collisions, insertion order); `map.get()` returns `V | undefined` so the miss must be handled, and it returns a **reference** so `push` needs no second `.set()`; `.join` hangs off the array in JS, not the separator; no dict comprehension - the annotated loop beats `Object.fromEntries`, which types too loosely. **Aliasing & `readonly`**: returning the caller's array wires the two together in both directions and silently desyncs the `count === characters.length` invariant - shallow-copy on the way out (deliberately shallow: protect the container, not the contents). Two distinct `readonly`s (property modifier vs `ReadonlyArray`), and `readonly` **parameters** are the good trick - `readonly T[]` isn't assignable to `T[]`, so the compiler _forces_ the copy rather than relying on discipline. It's erased at runtime and shallow. **Cartesian product as a fold**: variable-length `properties` means N nested loops are impossible, so cross one property in at a time with `flatMap` (which, unlike `map`, can grow a list); `[[]]` is the **identity** - one _empty_ combination, the "1" of products, since `[]` annihilates - and the `string[][]` annotation is required because `[[]]` infers `never[][]`. **Merging**: let the grid drive the output (`groups.get(label) ?? []`) rather than merging two collections - no dedup, no edge cases - which also forces the product to generate value **tuples**, not labels, since a blank row has no character to read `values` from. Also: comment _why_, not _how_ (language tutorials in code are noise); don't recompute a test's expectation with the implementation's own logic. See [lesson 04](./.lessons/04-phase1-combinations-and-cartesian-product.md).
